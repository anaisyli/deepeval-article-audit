# DeepEval-style Article Audit v1.8.11

Evaluate finished article bodies against only the knowledge files supplied by the user, with the current Codex model as judge and no evaluator API key. All judging rules, schemas and examples live in [references/method.md](references/method.md); this file is the run order.

## Required label

Write this label near every score and in every deliverable:

`DeepEval Faithfulness 规则复现（Codex 评审，非 DeepEval 官方运行）`

Never call the result an official DeepEval score or claim that the DeepEval package or its default evaluator model ran.

## Inputs

- Generic use: one or more finished articles plus their knowledge files, or a folder of article task subfolders. Several explicit knowledge files are allowed.
- `manage-article-knowledge` v0.5: pair `40_最终文章.md` with exactly one fact input, the current `30_本篇知识库资料.md`. Article-specific sources must first be consolidated by that Skill into the current `30/35`; never add them as parallel knowledge files.
- `manage-article-knowledge` v0.6 controlled run: read [the v0.6 adapter](references/manage-article-knowledge-v06-integration.md) and accept the request below. `prepare` locates and validates the installed knowledge Skill's handoff contract itself; do not open the knowledge Skill's SKILL.md, contract or references for an audit.

```text
handoff_event: faithfulness_request
handoff_contract_version, article_file, knowledge_file, project_id,
article_id, article_version, result_root, result_dir
```

Project paths belong to the knowledge Skill; do not search for or invent them. `result_dir` is the one version-specific directory for prepared, judgments, adversarial review and summary; process files stay in its `_work/` subdirectory (see Result directory layout). Reject a missing or incompatible contract version; never fall back to another local contract. Run without waiting for a second human instruction, then return `handoff_event: faithfulness_completed` with the same contract version. That event only means the artifacts exist and validated; the knowledge Skill still imports, migrates the task to `40_已完成` and issues `article_completed`. If it returns `writing_retry_required`, do not start: the writing Skill must first deliver a changed body.

Confirm pairing from filenames and content; ask one concise question only if several plausible pairings would change the result. Only the supplied knowledge files are `retrieval_context`: no web search, model memory, unrelated project files or the article itself.

## Independent context

Run the audit in a context that did not write the article: a subagent or a new session that receives only the request fields above. Keep the article-writing conversation out of it. The second evidence judgment (step 6) should likewise run in a separate subagent or fresh session that receives only `recheck-list` output plus the allowed knowledge, never the first pass's verdicts, evidence or reasons. If no separate context is available, perform a fresh pass without consulting the first conclusion.

## Review policy

New managed runs declare `review_policy: "decisive_recheck_v1"` in both inventories, `judgments.json` and `adversarial-review.json`:

- every frozen claim gets one primary evidence judgment;
- only claims the first pass judged `entailed` or `contradicted` get a second, blind evidence judgment;
- a first-pass `unknown` is final (`review_depth: first_pass_unknown`) and is never rechecked or promoted;
- a required recheck that is missing, disagrees or fails its checks becomes `unknown`.

Historical `two_pass_consensus` (every claim rechecked) and `risk_weighted_v1` (high-risk tags) results stay valid under their own rules and remain importable; do not add risk tags to new runs.

## Article-wide all-unknown gate

After primary judgments are assembled, check each article separately. If it has at least one frozen claim and every claim is `unknown`, pause that article before `recheck-list`, `check`, reconciliation, rendering, `faithfulness_completed`, or import. This is a quality-control stop, not a target to force a supported claim.

Inspect the frozen claims (`_work/claims.md`) against the allowed evidence in `_work/<article-id>-evidence-view.md`. Confirm that the allowed evidence was actually considered and that no direct statement or faithful paraphrase fully covers a claim's subject, predicate, scope, conditions, quantity, time/version, or asserted effect. Topic overlap and partial coverage do not count. Use no source outside this article's allowed knowledge files. This is a process-omission diagnostic only: it does not produce a second verdict, edit a judgment, or promote an unknown.

- If a direct match was missed, the audit view was not used, or the result remains doubtful, do not repair the existing verdicts or ask the blind reviewer to upgrade unknowns. For managed runs, use `audit_preflight.py reset --result-dir <dir>` and restart both extraction passes, freeze, all primary judgments, and required rechecks from scratch. For generic runs, restart from the original inputs in a fresh output directory. Do not carry claim IDs, verdicts, evidence rows, or reviews into the new attempt.
- If the diagnostic finds no missed direct support, preserve every unknown and continue the normal workflow. Briefly report that the all-unknown gate was checked and why the result stands.

An article without claims does not trigger this gate. In a multi-article batch, pause only the affected article unless a shared input or process error invalidates the others.

If an extraction pass turns out not to be independent (copied, merged or written with sight of the other pass), redo only that pass in a fresh subagent or session, freeze again, and then judge every frozen claim afresh and recheck afresh. Claim IDs change on every freeze, so never migrate old verdicts or reviews onto the new IDs by text match, never fill unmatched claims with one stock `unknown` reason, and never let the main judge write placeholder reviews. `freeze` rejects identical passes; both `assemble-*` commands reject one reason stamped on more than 3 claims.

`prepare` records raw SHA-256 values for traceability and locks the parsed audit inputs. `check`, `render` and `status` compare the article's parsed lines and units, the knowledge evidence chunks and line anchors, their allowed-evidence scope, and EC-1 identity contexts. Serialization-only changes that leave those parsed inputs unchanged (such as line endings, encoding, or table-edge pipes) do not invalidate an audit; a changed article unit, evidence chunk, line anchor, allowed-evidence scope, or identity context does. An old prepared artifact without the parsed fields falls back to its raw SHA-256. If `input_snapshot_changed` reports a parsed-input or intermediate-artifact conflict, stop and hand the article back to the knowledge base. Never delete and regenerate `prepared`, or refreeze under another file name to get past the check. Managed `prepare` still requires the current `30` bytes to match `writing_ready.json` (after the line-ending-only restore described below); allowing a serialization-only change during an already-prepared audit does not bypass the knowledge base's separate byte-binding checks at import.

Managed (v0.6) `prepare` accepts only the knowledge base's own task files: `04_文章任务/30_等待Faithfulness/<task>/40_最终文章.md` and its sibling `30_本篇知识库资料.md`, whose bytes must match `writing_ready.json`. When they differ only in line endings (LF, CRLF or a mix) and the permitted bytes are proven by the permit's SHA-256 (from the permit's own file if it still exists, otherwise from the current file with only its line terminators changed), `prepare` restores those bytes, reports `knowledge_restored` and continues, as the knowledge base's import does. Any other difference (text, BOM, encoding), a missing `30`, or a permit that is unreadable, lacks a valid hash, names another task's file or another article ID/version is refused as `input_snapshot_changed` and handed back to the knowledge base without touching the file. Never copy these files elsewhere or edit their version fields to start a new version; only the knowledge base issues versions. To measure or rehearse an audit without importing, run generic mode on the original files with `--output` to a separate directory.

Scripts are the only writers of audit records. A script refusal is a normal step of this workflow, not the end of the run: report its message, fix the cause at the step that produced it and continue. Before judging starts, correct exactly the rows a `freeze` error names in that pass file and run the same `freeze` command again; after judging, correct the named rows in the compact verdict or review file and run the same `assemble-*` command again. Until reconciliation an assembled record is rebuilt this way (the old one and the files built from it move to `_work/superseded-N/`); after reconciliation only `reset` remains. Stop and hand back only for `input_snapshot_changed` or a managed-input error the knowledge base must fix. Never hand-edit or script-edit an extraction pass after judging has started, never edit `judgments.json`, `adversarial-review.json` or a frozen file, never delete evidence rows to clear a check, and never rename an existing record (`*-before-*`, `*-corrected*`) to re-run a step that refuses to overwrite. Extraction passes decide atomic boundaries before any evidence is read (method §2): split independent predicates, conditions, causes or contrasts that could get different verdicts, and keep a homogeneous list under one subject and predicate as one claim. Extraction and judging are reading tasks done by the model itself: never generate a claim inventory, split sentences, or write verdicts or reasons with a script or template. `freeze` refuses a pass in which more than 10% of claims are phrase fragments rather than self-contained propositions; `assemble-judgments` and `assemble-review` refuse a reason that is shared by more than 3 claims once each claim's own ID, claim and quote are cut out of it. A compound-looking claim stays supported only when the second judgment's `atomicity_review` confirms one proposition (or its `atomicity_note` explains why); otherwise the reconciler keeps it unknown. Second-judgment rows mark a check `covered` only with a `claim_fragment` copied from the claim and an `evidence_fragment` copied verbatim from the knowledge file; `assemble-review` refuses anything else. If an attempt cannot be finished correctly before import (a gate names frozen records), run `python scripts/audit_preflight.py reset --result-dir <dir>`: it archives the attempt, including an unimported report, under `_work/attempt-N/`, keeps prepared and the view, and the audit restarts with two fresh extraction passes. Never patch an extraction pass of a judged attempt; `freeze` refuses once judging has started. An imported result is never reset.

Evidence must come from this article's own knowledge files: `assemble-*` rejects any other `source_file` and any quote that is not a verbatim span of the cited file, and the named claims must be re-judged, not stripped of evidence.

Distinguish a process failure from an audit-quality warning. A `render` command that exits successfully and writes its normal outputs has completed, even when the report contains `audit_quality: warning` or `audit_warnings`; those warnings are visible in the report and do not by themselves block rendering or import. Report the exact warning as a warning, not as a thrown exception or script refusal. Stop only on a non-zero command result, an explicit failed gate/receipt, or a missing required output. Do not infer a script error from warning text or from a continuation receipt whose `next_action` is `reconcile_and_render`.

## Speed rules

The model writes only semantic content; scripts copy every identity and mechanical field. Compact formats are in [audit-preflight.md](references/audit-preflight.md).

- When resuming an interrupted or paused audit, run `python scripts/audit_preflight.py status --result-dir <result-dir>` first. It reports each stage as done or pending, the compact shards present and the claim IDs still missing verdicts or reviews, without printing file contents. Continue at `next_stage` and read only the files that step needs; never reopen prepared, inventories, frozen, judgments or adversarial-review just to find out how far the audit got.
- Read the views, never `prepared.json` (it repeats the evidence per candidate, often 10–30×) or `frozen.json` (identity fields for the scripts). `_work/<article-id>-extract-view.md` holds the extraction guide and the article units without evidence, for the extraction passes; `_work/<article-id>-evidence-view.md` holds the knowledge files and allowed evidence, for judging and rechecking; `_work/claims.md` (written by `freeze`) lists the frozen claims one per line, for the judges. `_work/<article-id>-audit-view.md` is the full view, kept as the record.
- Never write the full `judgments.json` or `adversarial-review.json` by hand and never write ad-hoc Python to generate verdicts, reasons or checks: write the compact files and run the `assemble-*` commands. Templated reasons are downgraded by the validators anyway.
- Keep compact files terse in mechanical fields only; terseness never means fewer or coarser claims. Then: no classification row for a unit that has claims, no `claim` when an atomic claim equals its quote, notes only where method §2 requires them, and a short claim-specific `support`/`gap`/`conflict` phrase instead of a full `reason` sentence. These carry the same judgment in a fraction of the tokens; the old generator scripts existed only to get this terseness.
- Run independent work in parallel when the runtime offers subagents: the two extraction passes; primary-judgment shards (about 40 claims each, split by `claim_id` range, one compact file per shard); recheck shards; and whole articles in a batch. Each subagent gets only what it reads and writes: an extraction pass the extract view (its 抽取轮写法 section gives the file format and the allowed `non_factual` categories) and method §2; a judgment shard its range of `_work/claims.md`, the evidence view, method §3–§5 and the 主判断 section of audit-preflight.md; a recheck shard `_work/recheck.json`, the evidence view, method §3 and §6 and the 第二次判断 section. Give it the exact file paths; it reads nothing else: no knowledge-base folders, no `35`, no other article's files, no result directory of another version, and no other pass's or shard's output. Every audit starts both extraction passes fresh; a pass is never copied from another version or attempt. Without subagents run the same steps in sequence.

## Result directory layout

The version directory root holds only result files: `<id>-prepared.json`, `<id>-judgments.json`, `<id>-adversarial-review.json`, `faithfulness_summary.md`, `<id>_faithfulness_details.md`, `faithfulness_highlight.html`, plus the knowledge Skill's `unsupported-disposition.json` and `article_completed.json`. Every process file (reading view, compact passes, frozen union, replacements, verdict/review shards, recheck list, check receipts, backups, scratch scripts) goes in `<result-dir>/_work/`; prepare creates it. A successful managed render deletes `_work` (`--keep-work` keeps it for debugging); a failed render, a read-only revalidation and the generic mode leave it alone. Nothing downstream reads `_work`: the import, project validation and monthly report use only the root files. The render output lists any other root entry as `stray_files`; move such files into `_work` before rendering next time.

## Workflow

1. The orchestrating context needs this file and the commands below; it hands each subagent the method and audit-preflight sections listed under Speed rules instead of reading every reference itself, and opens audit-preflight.md when a command refuses. Without subagents, read method.md once per batch before judging. `references/record-format.md` (full record schemas, historical policies) is not needed for a run.
2. Prepare into an output directory that never overwrites sources. If `python` is unavailable, use the Python runtime of the current workspace.
   - v0.6: `python scripts/prepare_article_audit.py --article <40_最终文章.md> --knowledge <30_本篇知识库资料.md> --project-id <project-id> --article-id <article-id> --article-version <version> --handoff-contract-version <contract-version> --result-dir <result-dir>`
   - generic/legacy: `python scripts/prepare_article_audit.py --article <article.md> --knowledge <k1.md> [--knowledge <k2.md> ...] --output <article-id>-prepared.json`

   Both write the full, extract and evidence views into `_work/` (`audit_preflight.py view` rebuilds them for an older prepared). The preparer reads `文章ID`/`Article ID` metadata before the filename and, in v0.6, requires `文章版本`; a conflicting `--article-id` means the pairing is wrong. Managed commands reject identity mismatches, extra factual inputs, malformed `[result root]/[project-id]/[article-id]/v[version]/` directories and overwriting an existing core result. A managed `40` needs exactly one `<!-- ARTICLE_BODY_START -->` / `<!-- ARTICLE_BODY_END -->` pair; missing, repeated or reversed markers are a hard stop (ask the knowledge bridge to regenerate `40`). Tests use temporary directories; never hand-edit a real project's result JSON.
3. Two blind extraction passes (method §2), in parallel: each reads every non-structural unit of the extract view and, following its 抽取轮写法 section, writes its own compact `_work/first.json` / `_work/blind.json` (`coverage_review` + atomic `claim_inventory`) without seeing the other. Units marked 结构排除, `inventory_id` and `article_line` are filled by `freeze`.
4. Freeze the union with `python scripts/audit_preflight.py freeze --prepared ... --first-inventory ... --blind-inventory ... --output _work/frozen.json [--replacements _work/replacements.json]`. `freeze` also applies the renderer's coverage rules (categories, question/heading, reasons), so fix the rows it names and rerun the same command; it overwrites `_work/frozen.json` until judging starts, then refuses. It pairs the two passes' differently worded versions of one proposition automatically (`reworded_pairs` in its output), so passes need not agree on wording; it refuses only when, after pairing, they pick different propositions in too many units, or when one pass both lists claims for a unit and classifies it non_factual (keep one of the two, then rerun the same command). Never use the blind inventory alone, match by row position, or initialize a verdict from `inventory_origin`.
5. Primary judgment of every frozen claim (method §3–§5) into compact verdict files, then `python scripts/audit_preflight.py assemble-judgments --prepared ... --frozen-inventory ... --first-inventory ... --blind-inventory ... --verdicts _work/verdicts-1.json [--verdicts ...] --output <result-dir>/<article-id>-judgments.json`. Quote the article and evidence as exact raw substrings; leave out `line_start`/`line_end` (assembly fills them; a supported claim's quote must lie inside allowed evidence) and `source_file` (single knowledge file; otherwise the alias `F1`… or the view block `K0001`…). Never write `coreference_evidence`: assembly attaches and validates the EC-1 attribution block for every evidence quote that uses we/our/this…, `check` does the same for evidence it merges from a reviewer's rows, and a managed render fills any record still missing on a supported claim (and saves it with the judgments) instead of failing. Apply the Article-wide all-unknown gate before step 6.
6. `python scripts/audit_preflight.py recheck-list --judgments <article-id>-judgments.json --output _work/recheck.json` lists only the claims needing a second judgment, with identity fields and no verdicts. The blind reviewer writes one compact row per listed claim (method §6), then `python scripts/audit_preflight.py assemble-review --prepared ... --frozen-inventory ... --blind-inventory ... --recheck _work/recheck.json --reviews _work/reviews-1.json [--reviews ...] --output <result-dir>/<article-id>-adversarial-review.json`. The reviewer applies the same standard as the primary judgment (method §3): it judges against all allowed evidence in the evidence view, not only a sentence the first pass may have cited, and adds `evidence` rows for any other sentence it relies on (`check` merges them into the claim's evidence); a stronger or more specific statement in the source supports a weaker or more general claim, never the reverse, and a faithful paraphrase is support. Strict means no unsupported addition, not literal matching. Entailed rows give `atomicity_review` (status and a reason of at least 12 characters), a `challenge_reason` of at least 20 characters and every `entailment_checks` dimension the claim's wording requires (covered with both fragments, or missing); a dimension the claim does not need may be left out. `assemble-review` refuses a row that lacks any of these and lists every gap at once; the reviewer's conclusions (`split_required`, a dimension marked missing) are not gaps and become `unknown` at reconciliation. Contradicted rows need `challenge_reason`, `contradiction_evidence_fragment` and `contradiction_alignment`.
7. `python scripts/audit_preflight.py check --prepared ... --judgments ... --adversarial-review ... --frozen-inventory ... --receipt _work/receipt.json [--attempt 1]`. `review_tasks` lists only record problems (a missing review row, a citation outside allowed evidence, a field a hand-written record lacks), never the reviewer's conclusions. Fix them in the compact files, assemble again and rerun `check`; if any remain after that one correction, rerun with `--attempt 1` and they stay `unknown`. A completed historical result needs a new audit version.
8. `python scripts/reconcile_article_audit.py --result-dir <result-dir> --article-id <article-id>`. Reconciliation only retains or downgrades: a recheck marked `split_required` leaves that claim `unknown` (frozen claims are never re-split). No human queue.
9. Render once per batch: `python scripts/render_article_audit.py --input-dir <work> --output-dir <final>`; in v0.6 `--result-dir <result-dir> --article-id <id> --article-version <version>`, which removes `_work` after the reports are written. To revalidate after the knowledge Skill moved the task from `30_等待Faithfulness` to `40_已完成`, pass the moved `--article`/`--knowledge` and a separate `--output-dir` (read-only). The renderer may persist a missed reconciliation only when the real adversarial review exists; it never synthesizes an empty review.
10. Inspect Markdown and HTML. Identity, quotation or structure failures are fixed and rerun; semantic uncertainty is reported as `unknown`, never a reason to suppress reports.

## Mandatory outputs

1. `<article-id>_faithfulness_details.md`: one row per claim, with review depth.
2. `faithfulness_summary.md`: one row per article; keep the import-sensitive first seven columns, then unknown, contradicted and review depth. No DeepEval-compatible percentage.
3. `faithfulness_highlight.html`: every prepared unit as its own card in four human states (gray non-claim, green 明确支持, amber 尚未确认, red 明确冲突) with separate unknown/contradicted filters; claim, result, reason and quote stay in the same expandable card.
4. Prepared, judgments and adversarial-review JSON as the audit trail.

## Handoff

Tell the user which files were treated as article and knowledge, the claim count, the score and where outputs were saved. For v0.5/v0.6 hand off `<article-id>-prepared.json`, `<article-id>-judgments.json`, `faithfulness_summary.md` (plus `<article-id>-adversarial-review.json` for protocol 2.0) unedited in `result_dir`, and list the knowledge files in the exact order stored in `prepared.json`; the importer receives repeated `--knowledge` in that order. Never write the knowledge project's CSVs; the receiving Skill's `import_faithfulness.py` owns the import.

When grouping yellow/red claims for `manage-article-knowledge`, do not change the denominator, evidence judgments or three states. Compare each claim with existing Formal Claims first: one an existing claim already covers but `30` omitted is a material-pack omission; a real gap is grouped by a stable knowledge question answerable by the same evidence (same industry or "general packaging methods" alone is not a group; one question may hold any number of claims). A resolved gap covers only what its RES and Formal Claims answer; a new boundary of the same question is reopened by the knowledge Skill, a different question gets a new `gap_key`. The receiving Skill writes the disposition JSON, stating each `claim_id`'s relation to its specific question.

## Maintenance

This Skill delivers only the current article's artifacts. It never edits knowledge governance ledgers, KMR lists, Claim, RES, GAP, CUS, ANM or SKFB, never recomputes historical results, and never back-dates later evidence as attachment support. Update `CHANGELOG.md` whenever behavior, schemas, validation, output contracts or compatibility change; newest entry first, with date, user-visible effect and compatibility impact.
