# Run rules

Full rules behind the short run order in `SKILL.md`, moved here unchanged. Read only the section the current step names in `SKILL.md`, and do not reread a section within the same audit.

## Article-wide all-unknown gate

After primary judgments are assembled, check each article separately. If it has at least one frozen claim and every claim is `unknown`, pause that article before `recheck-list`, `check`, reconciliation, rendering, `faithfulness_completed`, or import. This is a quality-control stop, not a target to force a supported claim.

Inspect the frozen claims (`_work/claims.md`) against the allowed evidence in `_work/<article-id>-evidence-view.md`. Confirm that the allowed evidence was actually considered and that no direct statement or faithful paraphrase fully covers a claim's subject, predicate, scope, conditions, quantity, time/version, or asserted effect. Topic overlap and partial coverage do not count. Use no source outside this article's allowed knowledge files. This is a process-omission diagnostic only: it does not produce a second verdict, edit a judgment, or promote an unknown.

- If a direct match was missed, the audit view was not used, or the result remains doubtful, do not repair the existing verdicts or ask the blind reviewer to upgrade unknowns. For managed runs, use `audit_preflight.py reset --result-dir <dir>` and restart the first extraction pass, the coverage review, freeze, all primary judgments, and required rechecks from scratch. For generic runs, restart from the original inputs in a fresh output directory. Do not carry claim IDs, verdicts, evidence rows, or reviews into the new attempt.
- If the diagnostic finds no missed direct support, preserve every unknown and continue the normal workflow. Briefly report that the all-unknown gate was checked and why the result stands.

An article without claims does not trigger this gate. In a multi-article batch, pause only the affected article unless a shared input or process error invalidates the others.

## Resumed attempts and pass independence

The coverage review reads the first pass by design; it is not a second blind extraction. An attempt resumed from v1.8 with two blind passes keeps their rule: if one turns out not to be independent (copied, merged or written with sight of the other), redo only that pass in a fresh subagent or session, freeze again, and then judge every frozen claim afresh and recheck afresh. Claim IDs change on every freeze, so never migrate old verdicts or reviews onto the new IDs by text match, never mark unmatched claims `unknown` without judging them, and never let the main judge write placeholder reviews. In two-pass mode `freeze` rejects identical passes; both `assemble-*` commands reject one reason the model itself wrote and stamped on more than 3 entailed or contradicted claims.

## Input snapshot and managed prepare

`prepare` records raw SHA-256 values for traceability and locks the parsed audit inputs. `check`, `render` and `status` compare the article's parsed lines and units, the knowledge evidence chunks and line anchors, their allowed-evidence scope, and EC-1 identity contexts. Serialization-only changes that leave those parsed inputs unchanged (such as line endings, encoding, or table-edge pipes) do not invalidate an audit; a changed article unit, evidence chunk, line anchor, allowed-evidence scope, or identity context does. An old prepared artifact without the parsed fields falls back to its raw SHA-256. If `input_snapshot_changed` reports a parsed-input or intermediate-artifact conflict, stop and hand the article back to the knowledge base. Never delete and regenerate `prepared`, or refreeze under another file name to get past the check. Managed `prepare` still requires the current `30` bytes to match `writing_ready.json` (after the line-ending-only restore described below); allowing a serialization-only change during an already-prepared audit does not bypass the knowledge base's separate byte-binding checks at import.

Managed (v0.6) `prepare` accepts only the knowledge base's own task files: `04_文章任务/30_等待Faithfulness/<task>/40_最终文章.md` and its sibling `30_本篇知识库资料.md`, whose bytes must match `writing_ready.json`. When they differ only in line endings (LF, CRLF or a mix) and the permitted bytes are proven by the permit's SHA-256 (from the permit's own file if it still exists, otherwise from the current file with only its line terminators changed), `prepare` restores those bytes, reports `knowledge_restored` and continues, as the knowledge base's import does. Any other difference (text, BOM, encoding), a missing `30`, or a permit that is unreadable, lacks a valid hash, names another task's file or another article ID/version is refused as `input_snapshot_changed` and handed back to the knowledge base without touching the file. Never copy these files elsewhere or edit their version fields to start a new version; only the knowledge base issues versions. To measure or rehearse an audit without importing, run generic mode on the original files with `--output` to a separate directory.

## Script refusals and record writers

Scripts are the only writers of audit records. A script refusal is a normal step of this workflow, not the end of the run: report its message, fix the cause at the step that produced it and continue. Before judging starts, correct exactly the rows a `freeze` error names in that pass file and run the same `freeze` command again; after judging, correct the named rows in the compact verdict or review file and run the same `assemble-*` command again. Until reconciliation an assembled record is rebuilt this way (the old one and the files built from it move to `_work/superseded-N/`); after reconciliation only `reset` remains. Stop and hand back only for `input_snapshot_changed` or a managed-input error the knowledge base must fix. Never hand-edit or script-edit an extraction pass after judging has started, never edit `judgments.json`, `adversarial-review.json` or a frozen file, never delete evidence rows to clear a check, and never rename an existing record (`*-before-*`, `*-corrected*`) to re-run a step that refuses to overwrite. Extraction passes decide atomic boundaries before any evidence is read (method §2): split independent predicates, conditions, causes or contrasts that could get different verdicts, and keep a homogeneous list under one subject and predicate as one claim. Extraction and judging are reading tasks done by the model itself: never generate a claim inventory, split sentences, or write verdicts or reasons with a script or template. `freeze` refuses a pass in which more than 10% of claims are phrase fragments rather than self-contained propositions; `assemble-judgments` and `assemble-review` refuse a reason the model wrote that is shared by more than 3 entailed or contradicted claims once each claim's own ID, claim and quote are cut out of it; `unknown` gap types and reasons the assembler builds may repeat. A compound-looking claim stays supported only when the second judgment's `atomicity_review` confirms one proposition with the reviewer's own reason (or its `atomicity_note` explains why); otherwise the reconciler keeps it unknown. Second-judgment rows mark a check `covered` only with a `claim_fragment` copied from the claim and an `evidence_fragment` copied verbatim from the knowledge file; `assemble-review` refuses anything else. If an attempt cannot be finished correctly before import (a gate names frozen records), run `python scripts/audit_preflight.py reset --result-dir <dir>`: it archives the attempt, including an unimported report, under `_work/attempt-N/`, keeps prepared and the view, and the audit restarts with a fresh first extraction pass and coverage review. Never patch an extraction pass of a judged attempt; `freeze` refuses once judging has started. An imported result is never reset.

Evidence must come from this article's own knowledge files: `assemble-*` rejects any other `source_file` and any quote that is not a verbatim span of the cited file, and the named claims must be re-judged, not stripped of evidence.

## Warnings versus failures

Distinguish a process failure from an audit-quality warning. A `render` command that exits successfully and writes its normal outputs has completed, even when the report contains `audit_quality: warning` or `audit_warnings`; those warnings are visible in the report and do not by themselves block rendering or import. Report the exact warning as a warning, not as a thrown exception or script refusal. Stop only on a non-zero command result, an explicit failed gate/receipt, or a missing required output. Do not infer a script error from warning text or from a continuation receipt whose `next_action` is `reconcile_and_render`.

## Step details

### Step 2

2. Prepare into an output directory that never overwrites sources. If `python` is unavailable, use the Python runtime of the current workspace.
   - v0.6: `python scripts/prepare_article_audit.py --article <40_最终文章.md> --knowledge <30_本篇知识库资料.md> --project-id <project-id> --article-id <article-id> --article-version <version> --handoff-contract-version <contract-version> --result-dir <result-dir>`
   - generic/legacy: `python scripts/prepare_article_audit.py --article <article.md> --knowledge <k1.md> [--knowledge <k2.md> ...] --output <article-id>-prepared.json`

   Both write the full, extract and evidence views into `_work/` (`audit_preflight.py view` rebuilds them for an older prepared). The preparer reads `文章ID`/`Article ID` metadata before the filename and, in v0.6, requires `文章版本`; a conflicting `--article-id` means the pairing is wrong. Managed commands reject identity mismatches, extra factual inputs, malformed `[result root]/[project-id]/[article-id]/v[version]/` directories and overwriting an existing core result. A managed `40` needs exactly one `<!-- ARTICLE_BODY_START -->` / `<!-- ARTICLE_BODY_END -->` pair; missing, repeated or reversed markers are a hard stop (ask the knowledge bridge to regenerate `40`). Tests use temporary directories; never hand-edit a real project's result JSON.

### Step 3

3. First extraction pass, then a coverage review (method §2). The first pass reads every non-structural unit of the extract view and, following its 抽取轮写法 section, writes `_work/first.json` (`coverage_review` + atomic `claim_inventory`). Then a separate context (subagent or fresh session) reads the extract view and `first.json` and writes `_work/coverage.json`: for each unit the first pass classified non_factual, its own non_factual row if it agrees or the unit's claims if it does not, plus any independent fact the first pass missed in a claimed unit. It does not re-extract the article, rewrite or remove first-pass claims, or classify claimed units. Units marked 结构排除, `inventory_id` and `article_line` are filled by `freeze`.

### Step 4

4. Freeze with `python scripts/audit_preflight.py freeze --prepared ... --first-inventory _work/first.json --coverage-review _work/coverage.json --output _work/frozen.json`. It writes the second pass the later commands read (`_work/blind.json`: the first pass's claims plus the review's additions); never edit it. A unit is excluded only when the first pass and the review both classify it non_factual. `freeze` names any first-pass exclusion the review left without a verdict, a review row for a claimed unit, or a unit the review both claims and excludes; fix `coverage.json` and rerun. An attempt resumed from v1.8 freezes its two blind passes with `--blind-inventory _work/blind.json [--replacements …]` instead. `freeze` also applies the renderer's coverage rules (categories, question/heading, reasons), so fix the rows it names and rerun the same command; it overwrites `_work/frozen.json` until judging starts, then refuses. In two-pass mode it also pairs differently worded versions of one proposition (`reworded_pairs` in its output) and refuses when, after pairing, the passes pick different propositions in too many units. Never use the blind inventory alone, match by row position, or initialize a verdict from `inventory_origin`.

### Step 5

5. Primary judgment of every frozen claim (method §3–§5) into compact verdict files, then `python scripts/audit_preflight.py assemble-judgments --prepared ... --frozen-inventory ... --first-inventory ... --blind-inventory ... --verdicts _work/verdicts-1.json [--verdicts ...] --output <result-dir>/<article-id>-judgments.json`. Each row gives `semantic_status`; an `unknown` row adds `gap_type` (`no_evidence`, `partial_coverage`, `scope_broader`, `effect_or_purpose`, `subject_unclear`, `version_mismatch`, or `other` with a short `gap`), an `entailed` row adds its `evidence`, a `contradicted` row adds `evidence` and a short `conflict`. Quote the article and evidence as exact raw substrings; leave out `line_start`/`line_end` (assembly fills them; a supported claim's quote must lie inside allowed evidence) and `source_file` (single knowledge file; otherwise the alias `F1`… or the view block `K0001`…). Never write `coreference_evidence`: assembly attaches and validates the EC-1 attribution block for every evidence quote that uses we/our/this…, `check` does the same for evidence it merges from a reviewer's rows, and a managed render fills any record still missing on a supported claim (and saves it with the judgments) instead of failing. Apply the Article-wide all-unknown gate before step 6.

### Step 6

6. `python scripts/audit_preflight.py recheck-list --judgments <article-id>-judgments.json --output _work/recheck.json` lists only the claims needing a second judgment, with identity fields and no verdicts. The blind reviewer writes one compact row per listed claim (method §6), then `python scripts/audit_preflight.py assemble-review --prepared ... --frozen-inventory ... --blind-inventory ... --recheck _work/recheck.json --reviews _work/reviews-1.json [--reviews ...] --output <result-dir>/<article-id>-adversarial-review.json`. The reviewer applies the same standard as the primary judgment (method §3): it judges against all allowed evidence in the evidence view, not only a sentence the first pass may have cited, and adds `evidence` rows for any other sentence it relies on (`check` merges them into the claim's evidence); a stronger or more specific statement in the source supports a weaker or more general claim, never the reverse, and a faithful paraphrase is support. Strict means no unsupported addition, not literal matching. Entailed rows give `atomicity_review.status` and every `entailment_checks` dimension the claim's wording requires (covered with both fragments, or missing); a dimension the claim does not need may be left out. `challenge_reason` and `atomicity_review.reason` are filled from the fragments and status; the reviewer writes its own atomicity reason (at least 12 characters) only to keep a compound-looking claim `atomic`, and its own reason (at least 8 characters) only to rule a wording-signalled dimension `not_applicable`. `assemble-review` refuses a row that lacks any of these and lists every gap at once; the reviewer's conclusions (`split_required`, a dimension marked missing) are not gaps and become `unknown` at reconciliation. Contradicted rows need `contradiction_evidence_fragment` and `contradiction_alignment`; `challenge_reason` is filled from the fragment when left out. When every listed claim is entailed, `all_supported_challenge` is filled too.

### Step 7

7. `python scripts/audit_preflight.py check --prepared ... --judgments ... --adversarial-review ... --frozen-inventory ... --receipt _work/receipt.json [--attempt 1]`. `review_tasks` lists only record problems (a missing review row, a citation outside allowed evidence, a field a hand-written record lacks), never the reviewer's conclusions. Fix them in the compact files, assemble again and rerun `check`; if any remain after that one correction, rerun with `--attempt 1` and they stay `unknown`. A completed historical result needs a new audit version.

### Step 8

8. `python scripts/reconcile_article_audit.py --result-dir <result-dir> --article-id <article-id>`. Reconciliation only retains or downgrades: a recheck marked `split_required` leaves that claim `unknown` (frozen claims are never re-split). No human queue. It keeps the unreconciled records in `_work/pre-reconcile/`. If a claim both passes judged `entailed` was downgraded only for a record problem (a fragment or field, not a reviewer conclusion or a disagreement), do not `reset`: run `python scripts/audit_preflight.py reopen-review --result-dir <result-dir> --article-id <article-id>` once, before the knowledge base imports. It archives the rendered result to `_work/reopened-1/`, restores the unreconciled records and lists the claim IDs to fix; correct only those rows in `_work/reviews-*.json` (their conclusion stays `entailed`; `assemble-review` refuses any change to other claims' rows), then rerun `assemble-review`, `check`, reconcile and render. `reset` stays for the all-unknown gate and for a pass that was not independent.

### Step 9

9. Render once per batch: `python scripts/render_article_audit.py --input-dir <work> --output-dir <final>`; in v0.6 `--result-dir <result-dir> --article-id <id> --article-version <version>`, which removes `_work` after the reports are written. To revalidate after the knowledge Skill moved the task from `30_等待Faithfulness` to `40_已完成`, pass the moved `--article`/`--knowledge` and a separate `--output-dir` (read-only). The renderer may persist a missed reconciliation only when the real adversarial review exists; it never synthesizes an empty review.

### Step 10

10. Inspect Markdown and HTML. Identity, quotation or structure failures are fixed and rerun; semantic uncertainty is reported as `unknown`, never a reason to suppress reports.

## Grouping for manage-article-knowledge

When grouping yellow/red claims for `manage-article-knowledge`, do not change the denominator, evidence judgments or three states. Compare each claim with existing Formal Claims first: one an existing claim already covers but `30` omitted is a material-pack omission; a real gap is grouped by a stable knowledge question answerable by the same evidence (same industry or "general packaging methods" alone is not a group; one question may hold any number of claims). A resolved gap covers only what its RES and Formal Claims answer; a new boundary of the same question is reopened by the knowledge Skill, a different question gets a new `gap_key`. The receiving Skill writes the disposition JSON, stating each `claim_id`'s relation to its specific question.
